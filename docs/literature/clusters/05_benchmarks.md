# 簇五：Benchmark 与评测对象

**Benchmark 只告诉我们任务是否完成，不能单独证明模型学会了 Harness 能力或改进器变强。**

Benchmark 不是方法论文。它们规定任务、环境和评分方式，决定我们能否把“当前运行更强”“学生学会了”“改进器更会改进”分开。使用 Benchmark 时，必须固定版本、任务划分、模型、工具权限和预算。

## SWE-bench

**SWE-bench 把真实 GitHub issue 交给 coding Agent，让它修改仓库并通过项目测试；它提供了长程代码修复环境，但测试通过仍不能覆盖所有行为正确性。**

### 🧩问题背景

代码补丁不是一次文本生成，而是理解仓库、定位文件、运行测试、修改和回归验证的多步过程。失败可能来自定位、工具调用、测试解释或补丁本身，最终 reward 往往到测试结束才出现。

### ⚙️核心方法/评测协议

每个实例包含 issue 描述、代码仓库和评测测试；Agent 在受限环境中编辑代码，最终以测试是否通过作为主要判据。SWE-bench Verified 是经过人工筛选的子集，适合减少问题描述歧义。

### 📊实验结果

| 指标 | 评测含义 | 对当前项目的提醒 |
|---|---|---|
| pass rate / resolved rate | 测试通过的 issue 比例 | 必须报告模型、Harness、并发/时间预算和版本 |
| patch 与测试日志 | 过程证据 | 可以用于定位首次偏离和修复动作，但不能把最终通过当成每一步都正确 |

论文/报告之间的绝对数字随模型、Harness 和 split 变化；本卡片不把不同版本的 pass rate 拼成一个排行榜。SWE-bench 本身也不报告“训练后撤去 Harness 的能力保留”。

### 🔗谱系位置

SWE-bench 是 DGM、SICA 等 coding RSI 工作常用的评测对象。它适合验证代码级结构性 RSI，却不能单独证明通用长程推理或模型—Harness 协同演化。

### ⚠️局限

1. 测试套件可能不覆盖 issue 的全部语义，过拟合测试存在风险。
2. 仓库、依赖和执行时间造成较高环境成本；失败未必来自推理。
3. 不同 Harness 的工具、上下文和自动修复策略会改变难度，跨论文数字不能直接比较。

**来源：** Jimenez et al., *SWE-bench: Can Language Models Resolve Real-World GitHub Issues?*, ICLR 2024, arXiv:2310.06770；SWE-bench Verified 为后续评测子集。

## OSWorld 2.0

**OSWorld 2.0 把 Agent 放进真实桌面/应用交互环境，要求完成跨应用操作；它适合观察长程状态和工具错误，但桌面环境的重置、版本和视觉输入会影响可重复性。**

### 🧩问题背景

Web/桌面任务需要点击、输入、文件操作和跨应用状态维护，文本回答对了不代表任务完成。失败发生在“动作链中任何一个 UI 状态或权限理解错误”。

### ⚙️核心方法/评测协议

任务提供自然语言目标，Agent 通过 GUI 或应用工具执行，环境按任务测试条件判定完成。OSWorld 2.0 扩展了任务与应用覆盖，强调长程交互、环境状态和更严格的评测。

### 📊实验结果

| 指标 | 评测含义 | 对当前项目的提醒 |
|---|---|---|
| task success / completion | 任务最终是否达到测试条件 | 应同时保存每一步动作、观察和失败位置 |
| 应用/任务分布 | 不同软件和跨应用场景 | 训练、开发和测试要按任务语义划分，防止模板泄漏 |

不同论文使用的 OSWorld 版本、视觉模型和工具权限不同；论文未提供一个与当前 K、h0、SFT 预算可直接对齐的统一数字。

### 🔗谱系位置

OSWorld 2.0 是 RSIAgent 等记忆/探索方法的评测环境，也是当前 IDEA 可选的长程环境。与 AppWorld 相比，它更强调桌面状态和视觉动作；与 SWE-bench 相比，环境随机性和重置成本更高。

### ⚠️局限

1. 桌面应用版本、分辨率、网络和权限会造成结果漂移。
2. 最终成功标签稀疏，难以直接判断哪一步导致失败。
3. 视觉定位、工具格式和环境故障可能掩盖模型的长程推理问题，因此必须保留可重放日志和失败分类。

**来源：** OSWorld/OSWorld 2.0 项目论文与官方 benchmark 文档；Note.md 只记录名称和用途，具体版本、作者与数值需在实验协议中锁定后补录。

## 评测选择建议

第一轮不要同时上所有 Benchmark。先选一个可以重置、能保留动作历史、具有程序化验证器的环境，完成以下最小对照：

| 对照 | 推理时支持 | 训练 | 部署时保留 | 要回答的问题 |
|---|---|---|---|---|
| B0 | h0 | 无 | h0 | 学生原始能力和环境是否可用 |
| B1 | h0 + 固定 K | 无 | h0 + K | K 是否能即时救场 |
| B2 | h0 + 固定 K | 接受轨迹 SFT | h0 | 轨迹是否被内化 |
| B3 | h0 | 自训练/普通教师对照 | h0 | K 是否提供了超出通用教师的学习信号 |

只有 B2/B3 在未见任务上有稳定差异后，才有必要把 Benchmark 用来评估 K 的代际更新和 A 的改进器收益。
