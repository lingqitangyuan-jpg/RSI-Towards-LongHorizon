## 1. 先确定研究顺序

建议按下面的顺序推进：

**环境与评测可靠 → 外部指导确实有效 → 单轮能力内化 → 更新 Harness 的多轮价值 → 改进器自身的收益 → 完整实验、写作与投稿。**

每一步都应留下可以独立检查的产物。下一阶段是否展开，由前面的证据、可用资源和导师讨论决定。这样，即使完整 RSI 没有成立，也能知道失败发生在哪个环节，并保留有价值的机制分析。

第一阶段的目标可以很具体：**在一个可验证、有状态的环境中，让一个固定教师和固定 Harness 生成学生能够学习的轨迹；训练后移走教师，检查学生是否在未见任务上保留收益。**

### 1.1 把大 IDEA 拆成三个递进问题

| 层次 | 要回答的问题 | 支持它的核心证据 | 对应的研究主张 |
|---|---|---|---|
| Q1：内化 | 外部 Harness 诱导的长程行为，能否被学生在固定 `h0` 下学会？ | 审查轨迹 SFT 后，学生在无教师、无私有 K 的未见任务上优于原模型及普通自训练 | 长程控制行为可以被内化 |
| Q2：迭代 | 根据新学生的失败更新 K，是否优于持续使用强的固定 K？ | 相同轮数和可比预算下，更新 K 的学生曲线、长任务表现或成本更好 | 模型与 Harness 的迭代适配有价值 |
| Q3：改进器 | 演化后的 A，是否更会产生有训练价值的 K？ | 只交换 A，固定学生、初始 K、任务和预算，比较其下游独立学生收益 | 存在你笔记所定义的改进器收益 |

Q1 成立不自动推出 Q2；Q2 成立不自动推出 Q3。第一版项目优先把 Q1 做清楚，再用小实验判断是否继续 Q2、Q3。若最后以 Q1/Q2 为论文主体，也需要一个具体的新机制或新的可靠发现，不能把复现本身当成贡献。

### 1.2 已有工作与本项目的边界

- **Harness-Zero 已实现主要蒸馏链。** 私有参考 K 指导审查者，响应在执行前 PASS/REPLACE，接受响应进入学生轨迹，随后 SFT，部署只保留目标 Harness。其结尾也已提出“更强模型构建更好 Harness，再把收益返回权重”的递归愿景。[R1]
- **HyperAgents 提供可编辑元代理与程序继承机制。** 主实验冻结基础模型，演化任务代理和元代理的程序；没有完成你的学生权重蒸馏链。[R2]
- **本项目需要验证的部分**是具体长程失效机制的可内化性、多轮更新的增量，以及同起点条件下改进器是否更有效。把两个仓库连接起来是工程基础，仍需找到可检验的研究贡献。

这些是定向阅读结论，还不能代替完整的相近工作核查。

## 2. 先给初版系统划一个小范围

以下是一组便于开始的默认选择，后续可根据 pilot 改动，并记录原因。

| 对象 | 初版暂定做法 | 后续何时扩展 |
|---|---|---|
| 学生 `M` | 一个可训练、可重新部署的开源指令模型；先用一个规模 | 主结果稳定后再考虑第二规模或第二模型 |
| 部署 `h0` | 固定提示、工具协议、任务内文件系统、上下文上限与停止规则；先关闭额外子代理 | 有明确必要性时增加，并重新对齐所有对照 |
| 教师 | 一个固定的、能正确使用工具的强模型；与学生角色分开记录 | 需要研究弱教师或同模型自蒸馏时另做对照 |
| 私有 `K0` | 先复用参考 bank 或写一个小的机制包，并固定版本 | 单轮有效后，再允许改进器更新它 |
| 改进器 `A0` | 初期固定程序/提示，甚至可以先由人工按明确规则修改 K | 发现固定改进方法的瓶颈后，再做程序层演化 |
| `A` 的继承 | 先明确为代码、提示、诊断规则及经验资产的继承 | 元代理参数训练留作后续独立问题 |
| 任务分布 | 固定任务池，按依赖结构分组，保留未见任务 | 确有课程需求时，先加预设课程，再研究自适应课程 |
| 学习方法 | 先用 SFT/LoRA，打通一条训练链 | 有证据说明模仿学习不足时，再考虑偏好学习或 RL |

第一版最好只选择一种长程机制，例如**关键状态维护**或**可见错误的检测与恢复**。结合已有代码，一个值得测试的候选切口是：<u>*有限审查预算下，怎样选择检查位置，才能产生更有学习价值的长程轨迹*</u>。这里是**候选方向**，还不是已经确认的**创新点。**

“能力内化”应具体指：在 `h0` 已提供的基础设施上，模型学会更好的状态读写、检查、规划或恢复行为。文件存储、工具执行等基础能力仍由 `h0` 提供。

## 3. 项目准备：建立可工作的研究基础

### 3.1 先盘点资源，再决定训练规模

第一周建立一页资源记录，回答下列问题即可，不需要先购买设备或服务。

| 资源 | 要确认什么 | 对工作安排的影响 |
|---|---|---|
| 计算机器 | 本地 Windows、WSL2 或远程 Linux 是否可用；CPU、内存、磁盘 | 决定环境和容器在哪里运行 |
| GPU | 型号、显存、可用时段、是否独占 | 决定学生规模、上下文长度及训练并发 |
| 模型访问 | 学生权重和 tokenizer 能否获取；教师工具调用是否可用 | 决定模型组合及接口适配量 |
| 训练后端 | 可用的本地/服务器训练，或已有训练服务 | 决定是否沿用 HZ 的 Tinker 路径 |
| 经费与时间 | 一周可投入时间；API、GPU 与存储的初始预算 | 决定 pilot 上限和复现实验规模 |

只有 CPU/API 条件时，仍可先完成环境、裸学生、教师指导、轨迹审计和小规模训练路径验证；正式权重内化需要可训练后端。显存较少时，先尝试更小模型、LoRA/QLoRA、低并发与顺序执行。模型是否能训练，要同时看序列长度和训练实现，不能只按参数量判断。

### 3.2 环境搭建的推荐顺序

推荐在 **Linux 服务器或 WSL2 的 Linux 环境**执行实验，Windows 负责编辑、阅读与查看结果。`Project` 是项目的统一根目录；远程执行时使用同一项目的同步副本，结果回到相同目录约定中。

1. **保留参考源码。** 现有 `sources/repo/` 作为阅读与版本参照；实验修改放进自己的工作副本或适配层。为自己的代码建立 Git 管理。
2. **建立采集环境。** 本地 HZ 要求 Python `>=3.12,<3.14`，固定 Harbor `0.21.0`，并使用 vendored deepagents。先保留锁文件，不在首次复现时同时升级依赖。[R3]
3. **验证 Docker 和任务环境。** 先确认镜像构建、启动、任务重置、工具执行和结束评分；使用官方环境校验或训练 split 的已知解做工程检查，测试答案不进入后续教师输入。
4. **验证模型协议。** 用单个任务检查消息格式、工具调用、reasoning/text 分离和错误返回；并发从 1 开始。
5. **单独验证训练路径。** 用极少量训练数据完成一次更新、保存、重载，再让新 checkpoint 无教师执行。先把“训练结果如何回到下一次 rollout”打通，再扩大采集。
6. **保存环境快照。** 记录 OS、GPU/驱动、Python、锁文件、镜像 digest、源码版本/哈希、模型和 tokenizer revision、模板与运行配置。

HZ 工作副本内可参考的无模型检查命令如下；这是后续操作示例，本次未执行：

```bash

uv sync --locked --group dev

```

本地训练环境可以后建，用 Transformers/PEFT 等实现 LoRA。HZ 自带训练路径依赖 Tinker；换成本地训练器需要适配数据、模板与 loss mask，不能假设安装依赖后即可直接替换。[R3]

## 4. 环境和任务怎么选

**暂定主环境先考察 AppWorld**，因为已有 HZ 的环境、审查和数据链可复用。但要先确认任务中确实存在你关心的状态依赖和长程失败，不因它是交互 benchmark 就自动满足研究需求。

| 环境选择 | 当前适合的用途 | 需要核实的边界 |
|---|---|---|
| HZ 自带较易运行的少量任务，如 SpreadsheetBench/USPTO | 1—2 个任务的接口、日志与训练链检查 | USPTO 的任务目标是单步逆合成，不能作为长程主证据 |
| AppWorld | 现有链条的主要候选，研究跨应用、多步状态操作 | 专用初始化和独立评分；按 scenario 处理相关任务；依赖长度需另外标注 |
| 轻量、可控的文本环境，例如 ALFWorld/TextWorld 类环境 | 环境受阻时的开发备选；控制依赖结构和恢复条件 | 不是无成本替换；要检查任务复杂度、适配与公开基线，简单任务易饱和 |

开始只选一个主环境。第二环境用于关键结论的迁移验证，是否加入取决于论文主张和资源。

### 4.1 明确什么叫“长”

优先根据**必须完成的前置条件、子目标依赖深度、信息保持跨度**划分短/中/长任务；实际环境动作数、模型回合数和 token 数另行记录。

如果能拿到可信参考计划，可以记录其有效长度；只有证明最优时才称“最短长度”。否则使用可审核的依赖标注作为代理，并抽查。一次 Bash 可以封装多次 API 操作，因此主模型调用数不能直接当作环境依赖深度。

至少保留两类未见评测：同类任务的新实例，以及更深依赖或新的依赖组合。只有训练未覆盖更长依赖区间时，才使用“长度外推”的说法。首版优先做可解释的泛化，不急着同时覆盖所有复杂度维度。

### 4.2 一开始就分好数据

- **训练/诊断集**：采集轨迹、分析失败、演化 K/A。
- **开发集**：选择 K、checkpoint、超参数和停止位置；多轮使用后也可能被过拟合，控制选择次数。
- **最终测试集**：协议与主要设计固定后评估；不把反馈交给改进器或用于调参。

按任务族、模板或 scenario 成组划分，再处理实例，减少近重复泄漏。AppWorld 如沿用已有 train/dev 合并配方，应从可用训练场景另留开发组，不能顺手把官方测试集当日常开发集。早期画曲线使用开发集；最终报告按冻结协议生成测试曲线，选择依据仍来自开发集。

## 5. 分阶段开展研究

时间只是参考。假设每周约 20—30 小时，可以先留出约 **4—8 个月到形成可投稿稿件**的窗口；环境获取、额外研究分支和个人学习会改变进度，评审与返修另计。各阶段可以重叠，也可以回退。

| 阶段 | 弹性用时 | 主要问题 | 可见产物 | 继续或调整条件 |
|---|---|---|---|---|
| P0：准备 | 1—3 周 | 能可靠运行、评分和加载训练结果吗？ | 资源与环境记录、一条完整日志、小训练重载记录 | 执行链可解释；受阻则缩小环境或换执行机器 |
| P1：现象与定位 | 1—3 周，可与P0重叠 | 存在什么长程失败？已有工作做到哪里？ | 失败案例、一页问题、相近工作表、指导前后开发结果 | 教师/K有有效信号；差异落到具体机制 |
| P2：单轮内化 | 2—4 周 | 学生能独立保留什么？ | 审计后的训练数据、一次SFT、无教师评测 | 比普通自训练有可信信号，再扩规模 |
| P3：多轮适配 | 3—6 周 | 更新K是否有额外价值？ | 固定K/更新K曲线、成本及旧任务回归 | 有增量才将多轮作为核心；否则回到单轮机制 |
| P4：改进器收益 | 3—6 周，条件性扩展 | A自身是否变强？ | 版本继承记录、只交换A的探针实验 | 同起点收益成立才支持更强RSI主张 |
| P5：正式证据 | 3—6 周 | 结果稳健、可解释、可复现吗？ | 重复实验、独立测试、关键消融与图表 | 主张与证据对应，剩余问题收敛 |
| P6：写作与投稿 | 3—5 周，草稿提前写 | 如何清楚交代问题、机制与边界？ | 完整稿、附录、复现材料、反馈与投稿包 | 与导师确定目标，按官方要求提交 |

### P0：把一条执行链跑透

最低要求是**一条任务的输入、学生响应、工具执行、环境观察、最终评分和日志能互相对上**。随后接一次**教师干预**，再进行一次小数据训练/重载练习。

如果训练基础还不熟，可以并行做一个小练习：理解 loss、反向传播、优化器更新、LoRA adapter 保存和加载。它的目标是帮助排查训练链，不作为研究实验。

环境连续几个工作日没有新进展时，记录阻塞位置并选择缩小配置、换 Linux 执行环境或先用轻量环境开发。不要在没有方向信号时，把大量时间投入全域 Docker 镜像和两套框架的整体合并。

### P1：确认问题和指导信号

从训练/开发任务中选一个小的分层样本，例如先看 20—50 个任务或可获得的代表性轨迹。这个数量用于估计失败类型、成本和可行性，不用于宣布显著提升。

先比较：`原学生+h0` 与 `原学生+h0+固定教师/K0`。人工追踪部分失败和成功，区分工具格式问题、状态遗忘、目标偏移、错误未发现、恢复失败及预算耗尽。检查教师是否真的给出了学生可执行、可理解的下一步。

并行做有边界的相近工作核查：从两篇论文及 HZ §2 的模型—Harness 共演化相关工作出发，补读最相近的原文，必要时向前向后追引。维护简表：更新对象、是否固定部署 Harness、是否多轮、是否验证长程、是否测改进器收益、你的实际差别。当前尚未完成这项核查，不能预先写“首次”。

本阶段结束时，用一页写下：一个具体失败机制、一个候选解决机制、一个能推翻它的对照，以及当前计划声称什么。每周更新一次就够。

### P2：完成第一次能力内化

先保持 M、教师、K0、h0 和任务分布固定。跑通：

**学生提议 → 执行前审查 → 接受响应执行 → 独立环境验证 → 数据审计 → SFT → 无教师学生评测。**

第一轮优先比较下面四项：

| 条件 | 主要用途 |
|---|---|
| B0：原始学生 + h0 | 原始能力 |
| B1：原始学生 + h0 + 教师/K0，不训练 | 确认外部指导有效；它是参考条件，不是学生性能的数学上界 |
| B2：学生自身可验证轨迹 → SFT → h0 | 排除普通成功轨迹自训练的收益 |
| B3：经K0审查的轨迹 → SFT → h0 | 核心内化条件；评测移走教师和K |

先做 B0/B1，再决定是否采集 B2/B3。正式论证 K 的增量时，加入“同教师但无 K 的通用审查→SFT”，避免把教师本身的强能力都归给 Harness。

数据先从能承担的小批开始；第一次训练前先审计少量完整轨迹，之后根据有效样本、长度分布和成本扩采。可先用成功轨迹建立简洁链条；之后有明确恢复假设时，再比较恢复片段或其他失败数据利用方法。HZ 各领域的数据筛选并不完全相同，不能把“只成功”视为唯一正确规则。[R1]

**继续条件**：B3 在未见开发任务、无教师部署下出现可重复的收益，并能解释相对 B2 的差别。若只有训练集收益或指导执行成功，暂不扩展外循环。

### P3：固定改进器，测试多轮更新 K

单轮有信号后，先试少量轮次，例如 2—3 轮。改进器 A0 暂时固定，只根据当前学生失败修改 K。

- **对照组**：固定一个认真选择过的强 K0，每轮重新采集并训练。
- **实验组**：相同学生起点与轮数，每轮由 A0 更新 Kt，再采集与训练。

保持任务池/课程、教师和训练配方可比，记录所有候选的搜索成本。固定 K 组也要得到同样的多轮训练机会；再考虑相近总预算的一次性大训练，检查多轮优势是否只是多采样、多训练。

每轮在无教师 h0 下复测新任务与旧任务。若更新 K 只提升指导时的成功率，却不提升蒸馏后的学生，候选评价目标就需要调整：**强教师轨迹和高训练价值轨迹不一定相同。**

不要同时加自动课程。先固定短/中/长任务混合，看到数据饱和或覆盖缺口后，再试预设课程；只有它仍留下明确问题，才研究课程自我演化。

### P4：按需引入改进器演化

如果 A0 出现具体瓶颈，例如反复忽略同类错误、不能利用历史评估、候选成本失控，可以允许 A 的诊断、候选提议、检索或预算分配程序被修改。先限于可版本化程序资产；基础教师模型和外层评测保持固定。

借鉴 HyperAgents 的父代、补丁和档案机制即可。用一个薄的外循环调用采集/训练链，接口只传：`学生checkpoint、K版本、任务清单、预算`，返回：`数据路径、指标、成本、新checkpoint`。先不整体合并两仓库。

每个候选记录父代、修改内容、修改理由、评估结果和接受依据。导入成功、进入档案、任务表现提高和更会产生后继，是不同状态。

**最重要的实验是只交换 A：**

1. 从相同的冻结学生 M*、初始 K0、适应任务和预算出发。
2. 分别冻结 A0、At，让其提出/选择 K，并采集数据；两侧使用相同教师和训练配方。
3. 从同一个 M* 分别训练学生，由开发集选择，再在未见探针任务上比较无教师收益与成本。
4. 两侧提供相同的目标域历史和起始资源。At 的通用经验可以是继承资产，但不得夹带目标测试答案或额外任务解。区分“完整继承资产”的收益和“仅程序变化”的收益。

探针任务与产生 At 的源任务隔离。这样可以减少更强 Mt、更好 Kt 或更多目标域信息造成的混淆。资源充足时再补 `A0/At × M0/Mt` 的交叉实验。

若这里只能证明学生更强，或固定 A0 已足够，就相应收缩论文主张。多跑几轮本身不构成改进器能力增强的证据。

### P5：补齐正式论文所需证据

根据最终主张选择实验，不要求把所有消融都做一遍。优先保留：

1. **主结果**：固定 h0、无教师部署的成功率，按依赖档分组。
2. **核心反事实对照**：普通自训练、固定 K 或固定 A，针对最终机制保留最关键的比较。
3. **过程解释**：选择一到两个可靠可测的指标，如关键约束保持、已知错误后的恢复率、后段审查覆盖；首错位置难以准确标注时，不伪造精确标签。
4. **泛化与保留**：未见模板/组合、更深依赖，以及旧任务回归；主张跨环境时再补第二环境。
5. **成本与重复性**：所有条件的采样、搜索、训练和部署成本；多次独立重复及不确定性。

预先写下候选/checkpoint 的选择规则、主指标、失败/重试处理和停止条件，再看最终测试。扩展实验应由尚未解决的问题驱动。

### P6：从证据形成论文，再完成投稿与返修

写作从 P1 开始：先写问题和实验设计，后填结果。建议先有四类核心图表：方法/数据流图、成功率随依赖深度的曲线、多轮收益与累计成本曲线、关键对照与消融表。只有做了改进器实验，才加入对应结果图。

形成稿件后，请导师或同学重点检查：为什么是长程问题、现有方法差在哪里、对照是否公平、去掉教师后是否仍有效、哪些结果只支持较弱主张。把批评转成“文字澄清、必要补实验、缩小主张”三类任务。

投稿前准备：完整正文与附录、准确引用、实验配置与种子、数据/模型/源码来源、小规模可复跑配置、主图表到原始运行的索引、适用的匿名化和使用声明。检查引用是否支持正文主张，摘要结论是否超过实验范围。

目标届次与投稿路径在稿件成熟后和导师确定。届时从 ACL/ARR 官方页面核对日期、适用审稿周期、commitment、匿名及格式要求；本规划不绑定某届截止日，也没有核查某个具体周期。[R7]

收到评审后，建立逐条回应表，记录意见、证据、修改位置与补实验。接受后完成终稿和工件整理；需要修改或再次投稿时，保存本轮版本并更新证据。研究完成的标准是问题、方法、证据和材料可以清楚交接，录用时间还受评审流程影响。

## 6. 从第一轮开始就守住的实验约定

### 6.1 审查协议和可学习性

- 原始学生提议、审查决定、接受响应、实际环境观察分别保存。学生只看到接受后的历史。
- 替换动作必须在 h0 合法，依据来自学生可获得的任务信息；需要新证据时，通过学生工具获得并写入可见轨迹。
- 局部 PASS、最终任务成功、训练后学生改善分别记录，三者不互相替代。
- 先采用执行前审查。若改为段末审查，已发生的动作不能靠改写文本撤销；需要显式恢复动作或真实快照回滚，并计入成本。
- 分别记录审查调用预算、替换预算和总教师 token。相同替换次数不等于相同审查成本。

### 6.2 训练数据质量

先抽查完整样本，后批量生成。确认：教师私有路径/审查元信息没有进入学生监督；官方示例没有误当目标；工具响应与调用对应；tokenizer、chat template、推理格式与部署一致；loss 只覆盖应学习的 token。

统计各依赖档的有效训练 token、长度、成功率、去重率和丢弃原因。不能为满足长度上限，把未完成长轨迹的前缀标成完整成功；需要切片时保留完成语义和必要状态。检查最长任务是否因过滤反而从训练集中消失。

### 6.3 成本公平性分两种口径报告

**同学习量**回答“数据是否更有价值”：尽量对齐有效 SFT token、优化步数和任务覆盖。**同总预算**回答“方法是否更划算”：限制采样、教师、搜索和训练的总开销。两种口径未必能同时严格满足，清楚说明即可。

成本应包括失败 rollout、被拒候选、A 的演化和 K 的搜索；另外可以报告 At 已得到后的复用/摊销成本。部署成本单独报告，避免把昂贵训练期教师与无教师部署混在一起。

### 6.4 重复、统计和基础设施失败

工程检查可用单种子；方向 pilot 可以先做约 3 条独立链。正式重复数依据链间波动和可承受的最小有意义差异确定，资源允许时可从 5 条链讨论起，样本不足就如实呈现不确定性。这些数字是起点，不是发表门槛。

任务比较采用配对设计和区间估计；AppWorld 按 scenario 聚类处理。区分任务采样、解码随机性、训练随机性和搜索随机性。同一改进器评测上千条任务，不等于做了上千次独立 RSI 实验。

infra 失败与能力失败分开标记，同时保留全部预定任务的分母，报告包含 infra 的总完成情况。重试策略预先固定，不能只保留各方法顺利运行的交集。多轮选择使用开发集，不能反复看测试后挑最高版本。

## 7. 遇到结果不理想时怎样调整

| 观察 | 优先检查 | 下一步可选调整 |
|---|---|---|
| 裸学生几乎全失败 | 环境、初始化、模型协议、工具格式、任务难度 | 先修接口或选有可解空间的任务/模型 |
| 教师/K 没有帮助 | K 是否加载、干预是否正确、教师能力、预算是否提前耗尽 | 简化并人工检查 K；暂缓训练 |
| 指导有效，训练后无收益 | checkpoint是否加载、mask/template、超长过滤、信息不可获得 | 缩到一种行为与小数据训练，逐项定位 |
| B3 不优于普通自训练 | 收益是否仅来自训练量、教师通用能力、成功筛选 | 重新检验机制；不直接堆多轮 |
| 单轮有效，更新K无增量 | 新K是否真覆盖新失败、固定K是否已饱和、数据量是否公平 | 转向单轮内化机制、适用边界或效率 |
| 多轮有效，At没有额外收益 | 是否只继承更强学生/K、A变化是否有效、探针预算是否足够 | 保留共适应结论，收缩狭义RSI主张 |
| 长档退化或旧任务遗忘 | 长度覆盖、截断/丢弃、审查后段缺失、数据混合 | 调数据与预算，复查旧任务，再决定是否扩方法 |
| 自动课程只在自产任务提高 | 依赖定义、任务族泄漏、验证器、独立迁移 | 固定外部任务分布，重新验证学习价值 |

建议为每个小实验写一个有限预算和停止点。连续若干次受控尝试仍无信号时，整理负结果、检查替代解释并与导师讨论。负结果只有经过充分核验和清楚的问题化，才可能形成论文价值；流程完整本身不保证贡献成立。

## 8. 近期如何安排

### 8.1 第一周：争取一条可追溯执行

| 时间块 | 行动 | 最小产物 |
|---|---|---|
| 第1天 | 用已有分析画自己的数据流，列资源与待定选项 | 一页“固定什么、更新什么” |
| 第2—3天 | 准备Linux/WSL或服务器、依赖与Docker；跑无模型校验 | 环境记录，或准确的阻塞记录 |
| 第4天 | 做小训练/adapter重载练习；资源未到先理解和准备数据格式 | 一次练习记录 |
| 第5—6天 | 跑1—2个训练任务，人工核对输入、动作、观察和评分 | 一条完整可追溯日志 |
| 第7天 | 写周报，决定下周唯一主要问题 | 下一周目标和预算 |

这是一组时间块，不要求每天严格完成。第一周取得资源清单、环境进展和一条执行证据就有价值，不要求完成蒸馏。

### 8.2 第一个月争取回答的问题

环境能否稳定运行？选定任务是否存在明确长依赖失败？固定教师/K 是否能改善它？训练结果能否重新部署？最相近工作与你的候选机制究竟差在哪里？

如果月底仍主要卡在环境，则优先降低环境复杂度；如果工程已通却没有指导信号，则调整任务/机制；如果单轮已有可信信号，再安排多轮实验。按答案推进，不把日历当作必须进入下一阶段的理由。

### 8.3 每周只维护三个东西

1. 一页周报：本周问题、实验ID、证据、当前解释、下周唯一主要问题。
2. 一张实验表：配置/版本、任务划分、数据量、成本、主指标、失败原因、结论边界。
3. 本规划的简短变更记录：改了哪个选择、依据是什么、影响哪些已有结果。

学习内容按眼前瓶颈补：先理解工具调用、Linux/Docker 和 SFT/LoRA，再补实验统计与版本溯源；RL、复杂搜索和元模型训练等到它们确实成为研究需要时再深入。
