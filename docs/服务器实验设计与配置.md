## 1. 这份文档解决什么问题

近期目标是先确定 AppWorld/Harness-Zero 实验链可靠，再用最小规模实验回答两个问题：

1. 裸学生在固定部署 Harness 下能否稳定完成选定的长程任务；
2. 固定参考 Harness/教师的执行前审查是否改善学生轨迹，且改善是否足以进入后续能力内化实验。

因此服务器阶段先做 **P0：单任务执行链验收** 和 **P1：B0/B1 诊断对照**。P0/P1 不训练、不运行 RSI 外循环、不使用测试集选模型或超参数。只有 P0/P1 有清晰信号，才进入审计数据、LoRA/SFT 和多轮 K 更新。

对应配置合同见 [`configs/server/a100_p0_p1.toml`](../configs/server/a100_p0_p1.toml)。该配置的路径和模型字段是占位符，不能直接当作服务器现状。

## 2. A100 资源策略

### 2.1 默认原则

- 20 张 A100 是可用资源上限的线索，不是本项目的默认并行额度。
- P0/P1 从单 GPU、低并发和可重跑作业开始；不因 GPU 数量多就同时启动 20 个条件。
- 一个作业的 GPU 数、CPU、内存、临时盘和最长时间都写入作业配置，便于解释排队、抢占和失败。
- GPU 数量不是实验重复次数。重复实验按独立随机种子、独立 rollout 链或预先定义的任务配对统计。
- 每个阶段设 GPU-hour 上限；排队时间不计入 GPU-hour，但要记录等待时间和实际运行时间。

### 2.2 建议的初始资源档位

| 用途 | GPU | 并发 | 资源建议 | 说明 |
|---|---:|---:|---|---|
| `env-check` | 0 或 1 | 1 | 2--4 CPU，8--16 GB RAM，15--30 分钟 | 只检查依赖、镜像、路径和驱动，不跑模型 |
| P0 单任务 | 1 | 1 | 4--8 CPU，16--32 GB RAM，30--60 分钟 | 完整 `reset -> action -> observation -> verifier` |
| P1 B0 | 1 | 1 | 4--8 CPU，16--32 GB RAM，最多 30 分钟/任务 | 裸学生，固定任务清单和配置 |
| P1 B1 | 1 | 1 | 4--8 CPU，16--32 GB RAM，最多 30 分钟/任务 | 同一学生、任务和预算，启用固定 K/审查器 |
| 单次 LoRA pilot | 1 | 1 | 24--48 GB RAM，按模型上下文调整 | P0/P1 通过后再申请；不与诊断 rollout 混跑 |
| 多卡训练/大模型 | 2--8 | 1 | 由显存和训练器实测决定 | 仅在单卡瓶颈被证明后申请 |

P0/P1 的初始总预算建议不超过 **12 GPU-hours**。若单任务耗时或模型加载远高于预期，先缩小任务数或模型规模，记录调整原因，再申请更高预算。

### 2.3 排队友好的作业拆分

把一次长实验拆成可独立恢复的作业：

1. `env-check`：无 GPU 或短 GPU 作业，运行一次即可保存快照；
2. `p0-one-task`：一个任务一个 run 目录，失败可只重跑该任务；
3. `p1-b0`：按任务分片提交，但初始并发保持 1；
4. `p1-b1`：使用与 B0 完全相同的任务分片和预算；
5. `aggregate-p0-p1`：CPU 作业汇总结果、检查分母和生成诊断表。

初始不建议为 B0/B1 同时申请大量 GPU。若队列很长，可先提交 P0，排队期间在 CPU 上完成配置审查、任务分组、日志 schema 和本地小 mock 测试。若调度器支持数组作业，数组索引只能映射到固定任务清单，不能在作业运行时临时改变测试分组。

## 4. 版本与环境合同

### 4.1 软件版本

Harness-Zero AppWorld 适配当前按以下约束准备：

- Python：`>=3.12,<3.14`；
- Harbor：`0.21.0`；
- AppWorld：`0.1.3.post1`；
- AppWorld 必须使用专用 `envs.appworld.agent:AppWorldMinisweAgent` 和 `envs.appworld.harbor_environment:AppWorldDockerEnvironment`；
- AppWorld 需要 Docker 或实验室批准的兼容容器运行时，以及官方数据；
- 使用锁文件安装依赖，不在首次验收时顺手升级依赖。

训练后端仍待确认。Harness-Zero 现有链路含 Tinker 相关路径；若改用 Transformers/PEFT 本地 LoRA，需要单独适配数据格式、chat template、loss mask、保存/加载和 rollout 回接，不能把“依赖安装成功”当作训练链已打通。

### 4.2 路径约定

## 5. P0：单任务执行链验收

### 5.1 目的与条件

P0 只回答工程问题：一个真实 AppWorld 任务能否由专用环境和 agent 从初始化执行到 verifier，并留下可对齐的观测与工具事件。它不证明 Harness 方法有效，也不把 toy/mock 运行当作 benchmark 结果。

默认使用一个训练 split 中、依赖长度适中的任务。任务 ID 固定写入 manifest；不使用测试集任务调接口或挑参数。

### 5.2 P0 运行顺序

1. 加载解析配置、环境快照和固定任务 ID；
2. 初始化 AppWorld 专用 environment/agent；
3. 记录 `reset` 返回的公开任务信息；
4. 学生产生 action，记录原始请求；
5. 执行合法 action，记录 observation、工具结果和错误；
6. 重复直到任务结束、verifier 判定或固定步数/时间预算耗尽；
7. 记录最终 verifier、退出原因、总步数、教师调用数（P0 应为 0）和运行成本；
8. 生成 `manifest.json`、`environment_snapshot.json`、`run_summary.json` 等产物。

### 5.3 P0 通过标准

P0 通过需要同时满足：

- environment 能启动并完成一次真实任务 `reset`；
- 每个 action 都能与对应 observation/工具事件按序关联；
- 任务结束原因明确，verifier 结果可读取；
- 日志中没有把私有参考信息写入学生可见轨迹；
- 作业可在相同 commit、配置和任务清单下重跑；
- 失败时能区分基础设施失败（镜像/驱动/超时/网络）和能力失败（非法 action、状态遗忘、目标未完成）。

若只完成环境启动、没有完整 verifier 结果，状态记为 `P0_PARTIAL`，不能作为 benchmark 分数。

## 6. P1：B0/B1 诊断实验

### 6.1 固定对象

P1 使用同一学生模型、revision、tokenizer、chat template、任务清单、解码参数、最大步数和 wall-time budget。B0/B1 的唯一区别是是否启用固定审查器/参考 K。

- **B0**：初始学生 + 固定部署 Harness `h0`，无 reviewer，不训练；
- **B1**：同一初始学生 + `h0` + 固定 `K0`/reviewer，不训练。

B1 是外部指导条件，用于确认 K/教师的执行信号是否存在；它不是训练后学生可以达到的数学上界。P1 不把教师输出直接写入学生监督，审查私有信息只进入 `audit_private.jsonl`。

### 6.2 初始规模与任务分层

- 先使用约 20 个训练/诊断任务，按 scenario 或 task family 分组；
- 如失败类型或方差不足，再扩展到最多 50 个诊断任务，并记录扩展原因；
- 另留 grouped dev split 供协议、K 和预算选择；
- 测试 split 在协议锁定后冻结，不能用于挑 K、checkpoint、停止轮次或重试规则；
- 按依赖深度、状态保持跨度和已知失败类型分层报告，不只报告总体平均值。

### 6.3 B1 审查预算

初始值沿用配置占位：每个 episode 最多 32 次 reviewer 调用、最多 8 次 replacement、最多 64 个 episode steps、单任务 wall time 最长 30 分钟。实际运行前可调整，但调整必须写入 resolved config，并在 B0/B1 之间保持可比。

必须单独统计：

- 审查后的 `PASS`；
- 审查后的 `REPLACE`；
- replacement 预算耗尽后直接接受的动作；
- 审查调用数、替换数、教师 token、学生 token；
- 最终 verifier 成功与否。

预算耗尽后的动作不能与真正审查通过的动作混为一个 PASS 指标。

### 6.4 P1 产物与验收

每个 run 至少输出：

```text
config_resolved.toml
environment_snapshot.json
manifest.json
run_summary.json
student_visible.jsonl
audit_private.jsonl
verifier_result.json
failure_taxonomy.json
```

P1 可进入下一阶段的最低信号是：

1. B0/B1 的任务分母、失败原因和成本可以完整对齐；
2. B1 在开发/诊断任务上对一个明确的长程失败机制出现可解释改善，或发现可靠的负信号；
3. 改善不是由任务清单变化、重试次数变化、教师信息泄漏或预算差异造成；
4. 至少抽查一批完整轨迹，确认学生只见到允许的公开信息和接受后的历史；
5. 基础设施失败比例足够低，或其处理规则已经固定并单独报告。

“教师指导成功”本身不等于“学生已经内化”。P1 通过后才可以设计 B2/B3 的数据审计和 LoRA/SFT pilot。

## 7. 显存、LoRA 与多卡策略

### 7.1 先测实占用，再定模型规模

A100 可能是 40 GB 或 80 GB，不能按卡名推断显存。先记录 `memory.total`，再用目标模型、最长上下文和实际 batch 做短时显存探针。推理显存、KV cache、工具环境和训练 optimizer 状态要分别估计。

P0/P1 推理优先使用单卡、batch 1、低并发和固定上下文上限。超长任务应记录截断、超时和 OOM，不要悄悄降低上下文后继续合并结果。

### 7.2 LoRA/QLoRA 初始建议

只有 P0/P1 信号稳定后才做第一次训练。初始可选：

- 单卡 LoRA，较小可训练模型，batch 1，梯度累积控制有效 batch；
- 显存不足时评估 QLoRA，但保存量化配置、计算 dtype、量化库版本和基座 revision；
- 序列长度先按完整轨迹分布设置，明确最大长度和超长样本处理；
- 先只训练一个 adapter，保存 adapter、训练配置、数据清单和基座索引；
- 训练后立即重载 checkpoint，在无教师 `h0` 下跑一个固定探针任务，验证“训练结果能回到 rollout”。

LoRA rank、alpha、学习率、步数和最大长度属于开发集选择项；测试集冻结后不得根据测试结果挑选。训练数据只能使用 `student_visible.jsonl`，不得包含 `audit_private.jsonl`、verifier 私有字段或测试答案。

### 7.3 何时申请多卡

多卡只在下列情况之一成立后申请：

- 单卡模型加载或目标上下文明确 OOM；
- 单卡训练吞吐成为已测量的主要瓶颈；
- 需要比较的模型规模无法在单卡保持公平上下文和 batch；
- 训练器已明确支持多卡并完成一个可重载 pilot。

多卡配置需要记录并行策略（data/tensor/FSDP/DeepSpeed 等）、跨卡通信、每卡显存、总 GPU-hours 和 checkpoint 兼容性。多卡不会自动提高研究证据质量；若单卡足以验证机制，优先保持单卡以便重跑和排队。

```bash

git rev-parse HEAD
uv --version
docker --version
nvidia-smi
```

## 9. 运行目录与数据边界

建议的单次运行结构：

```text
rsi-runs/
└── 20261022_p1_b1_<run-id>/
    ├── config_resolved.toml
    ├── environment_snapshot.json
    ├── manifest.json
    ├── scheduler.json
    ├── student_visible.jsonl
    ├── audit_private.jsonl
    ├── verifier_result.json
    ├── failure_taxonomy.json
    ├── stdout.log
    └── stderr.log
```

边界规则：

- `student_visible.jsonl` 只包含学生在部署时可见的任务、历史、工具响应和接受后的动作；
- `audit_private.jsonl` 保存原始提议、审查决定、替换理由、私有 K 元数据和预算事件；
- verifier 内部状态、测试任务答案和开发选择记录不得进入训练数据；
- 运行目录与大型 checkpoint 默认在 Git 外，通过 manifest 记录路径、大小和校验值；
- 测试数据访问在协议锁定后冻结，并在 manifest 中记录访问状态；
- 若教师使用远程 API，日志中只保存请求哈希、模型 revision、token 用量和必要的脱敏响应，不保存密钥。

## 10. 安全、隐私与可复现性

- API key、SSH 私钥、cookie、数据库口令和服务器凭证只放环境变量或批准的 secret manager，不进仓库、不进日志；
- AppWorld 官方数据和可能含敏感状态的运行文件按实验室权限保存，提交和共享前先脱敏；
- 允许外网访问、镜像拉取、模型下载和容器挂载的范围由管理员确认；
- 容器使用最小权限和明确挂载目录，不能把用户主目录整体挂入任务容器；
- 每次运行记录 Git commit、依赖 lock、容器 digest、模型 revision、任务清单哈希和随机种子；
- 发生基础设施失败时保留原始日志和分母，不能用人工删除失败 run 的方式清理结果；
- 任何人工修改配置都要更新版本字段、变更记录和 resolved config。
