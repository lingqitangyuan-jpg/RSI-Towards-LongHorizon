# 项目骨架设计与选型决策

版本：v0.1，2026-10-22  
状态：MVP 工程骨架已建立；真实 benchmark、模型与训练后端尚未确定。

## 1. 研究流程在代码中的映射

本项目先验证一条可拆解的链路：固定学生在目标环境中执行任务，私有审查器按预算 PASS 或 REPLACE；执行后的公开交互轨迹可以转成训练样本；训练出的学生应在移除审查器后接受独立评测。只有这条链路可测之后，才扩展到更新改进器、Harness 与任务课程的多轮 RSI。

```text
BenchmarkTask ──> Environment ──> public Observation ──> Student proposal
                       ▲                                  │
                       │                         private Reviewer / budget
                       │                                  │ PASS or REPLACE
                       └──────── accepted Action <────────┘
                                  │
                    ┌─────────────┴─────────────┐
                    │                           │
          student_visible.jsonl       audit_private.jsonl
                    │                           │
              SFT exporter                error analysis
                    │
              model backend
                    │
          reviewer-free evaluation
```

奖励/verifier 只用于 episode 结束后的结果核验。公开训练轨迹不包含审核原因、私有任务记录或 verifier 输出；SFT 导出器拒绝非训练 split，并只读取 student-visible JSONL。

## 2. 两个参考仓库如何影响骨架

| 参考实现 | 采用的工程思想 | 本项目中的位置 | 保持可变的部分 |
|---|---|---|---|
| Harness-Zero | 候选动作的 PASS/REPLACE 审查；原始动作与接受动作分开；私有审计和学生轨迹分开；训练数据由接受后的轨迹生成 | `contracts.py`、`reviewers.py`、`runner.py`、`sft_export.py` | 不依赖其完整 Harbor、teacher provider、存储和 Tinker 训练栈；环境和训练后端通过协议接入 |
| HyperAgents | 候选资产要能记录父代、版本和评测关联；改进资产与评测结果需要分开保存 | `ArtifactRef`、`integrations/hyperagents.py` | 当前只提供 append-only archive 的小边界；不预设自动改进提示、父代选择算法、搜索策略或课程算法 |

这两个仓库分别覆盖“指导轨迹如何产生并进入模型”和“候选程序如何继承与评估”。本项目的研究对象是两者连接后的能力内化假设，因此先固定协议和证据边界，不把任何一方的全部工程栈作为前置依赖。

## 3. 当前代码模块与责任

| 模块 | 当前责任 | 真实实验阶段的扩展方向 |
|---|---|---|
| `contracts.py` | 公开任务、控制器任务、观察、动作、审查决定、结果与资产引用 | 增加版本化 schema、模型调用记录与跨运行 provenance |
| `benchmark.py` | 载入 TOML、校验任务 ID、固定 step budget 并生成 manifest 摘要 | 接入 benchmark 官方任务清单与划分校验 |
| `environment.py` | 定义 reset/step/verify 协议；含确定性 toy 环境 | 添加 Harbor/AppWorld 等 adapter；验证器保持环境信任边界内 |
| `policies.py` | 学生策略接口与故意漂移的 demo policy | 添加可替换模型 provider、解码和重试配置 |
| `reviewers.py` | 审查器接口与规则型 demo reviewer | 接入 Harness-Zero 风格私有 K 和固定 teacher |
| `runner.py` | episode 循环、review/replacement 预算、日志、结果分类 | 加并行调度、重试记录、成本计量与 checkpoint 关联 |
| `sft_export.py` | 训练任务公开轨迹转逐步 JSONL；每个样本带此前公开观察、接受动作和环境反馈作为 history | 增加 tokenizer/chat template、长上下文截断策略与 trainer 专用 adapter |
| `integrations/harness_zero.py` | 检查参考 checkout 的入口存在性 | 实现独立适配层，尽量复用目标 benchmark 的可信运行协议 |
| `integrations/hyperagents.py` | 保存有 lineage 的候选资产索引 | 加候选生成器、盲化评测、选择器和多轮实验编排 |

## 4. Benchmark 选择：暂定规则

目前不把 toy benchmark 当候选研究数据集。它只测试代码边界。正式环境优先选择满足以下条件的 benchmark：

1. 任务有可核查的跨步骤依赖，而不只是长输出或一次性问答；可以定义“长程”分桶，并记录依赖深度、有效操作数或状态转移数。
2. 每个 episode 能可靠 reset，最终评分可独立于模型生成过程（最好由环境终态、规则 verifier、单元测试等判定，而不是模型自己评自己，或生成过程影响打分），且训练时无法读取测试答案或测试 verifier 的私有状态。
3. 官方任务可以按任务族/模板分组划分，避免近重复任务跨 train/dev/test；有足够训练任务采集轨迹，也保留一次性冻结的测试集。
4. 工具动作、状态观察和步数预算可被统一记录；环境部署和 API 成本在现有算力下可承受。
5. 许可证、数据访问、模型调用条款和潜在污染风险可接受，结果可由别人按锁定版本复跑。

**AppWorld/Harbor 暂列第一候选，不视为已选定。** 原因是参考 Harness-Zero checkout 已含 AppWorld 专用 agent/environment 入口，便于核对 adapter 需求；这并不证明当前机器能部署成功、任务划分适合本研究，或该 benchmark 就是最佳选择。先完成一小批 task 的环境、verifier、分组和成本 pilot，再决定是否采用。可按相同标准评估其他带状态工具环境；若 AppWorld 的安装或任务划分不合适，保留 `Environment` 协议并替换 adapter。

### Benchmark pilot 必须回答

- 一个 task 从 reset 到 verifier 的最短完整运行是否稳定？失败能否区分模型失败、动作协议失败、环境故障与 verifier 故障？
- 长度/依赖深度是否反映真实的状态维护或错误恢复负担？短任务与长任务是否都有足够任务数？
- 任务族划分能否避免相同模板或实体组合的泄漏？任务说明是否已经包含私有答案线索？
- 关掉 reviewer 后，裸学生处于可学习但非饱和的成功率区间吗？reviewer 对 train/dev 的帮助能否由逐步日志验证？
- 单任务耗时、并发、容器、模型调用与 token 成本是多少？这决定 pilot 和主实验规模。

如果上述任一点不清楚，不进入大规模 SFT；先用少量任务检查 reset、接口、评分和可学习性。

## 5. 证据与隐私约束

- `TaskSpec` 是传给学生和 reviewer 的任务视图；`BenchmarkTask` 才含 split、深度、环境预算和私有字段。
- `Observation.metadata` 会递归拒绝当前定义的私有字段。接入新环境时仍需逐字段审计公开观察，不能把 adapter 自检当成 benchmark 隔离的替代品。
- 审计日志记录每次动作尝试，包括 reviewer 是否关闭或预算耗尽；审计文件不能作为普通学生训练输入。
- `summary.json` 和 verifier 结果属于评测材料。任何训练数据构建都必须明确选择 `student_visible.jsonl`，按 train split 导出，并记录导出器版本。
- step budget、review 次数和 replacement 次数要分别报告。`budget_passes` 表示审查器存在但预算耗尽后未经审查而继续执行的动作数。
- toy 漂移学生和规则审查器是测试夹具，不代表真实模型或有效教师，也不能用 toy 的成功率支持研究主张。

## 6. 建议的实施顺序

1. **资源盘点与环境 pilot：** 确认 Linux/WSL/服务器、CPU/GPU、存储、模型访问、容器能力和可用预算；在 AppWorld 与备选项中做小规模安装及 verifier pilot。
2. **锁定 benchmark protocol：** 固定 task ID、任务族划分、最大步数、工具 schema、reset 和评分规则；对 manifest 做哈希并留存版本。
3. **实现环境 adapter：** 不修改核心 runner；把 reset/step/verify 和官方评分映射到 `Environment`，增加单 task integration tests。
4. **建立真实策略接口：** 分别接入固定学生和固定 reviewer；单独记录模型/提示/解码版本、每步成本、timeout 和重试。
5. **完成采集与训练小闭环：** 在 train 上比较 bare 与 reviewed 轨迹，人工抽查 PASS/REPLACE、训练样本和隐私字段；再用小规模 LoRA 验证 checkpoint 能加载并 reviewer-free 推理。
6. **预注册式 pilot 决策：** 固定主指标、长程分桶、对照、运行预算与停止条件。先回答单轮内化，再决定是否进入 K 更新和 HyperAgents 风格改进器实验。

算力未定时，保持核心依赖标准库；模型 SDK、容器和训练框架放到可选 extras 或独立 adapter。不要为了预设 GPU 而把 CUDA、Tinker 或某个闭源 API 写进核心依赖。

## 7. 当前可以运行的 MVP

在 `Project` 目录运行：

```powershell
python -m unittest discover -s tests -v
python scripts/run_demo.py demo --manifest configs/toy_benchmark.toml --output runs/demo-001
python scripts/run_demo.py export-sft --manifest configs/toy_benchmark.toml --task-id toy-train-001 --trajectory runs/demo-001/reviewed/toy-train-001/student_visible.jsonl --output runs/demo-001/toy-train-sft.jsonl
```

demo 会对相同确定性学生运行 bare 和 reviewed 两种流程。当前刻意漂移的学生在 toy 环境不能自行恢复；规则 reviewer 可以纠正动作。该演示只说明 runner 按接口执行且日志分流正常。每次选择新的空输出路径，writer 会拒绝覆盖已有运行或训练数据。

## 8. 研究结论的边界

骨架通过不意味着 IDEA 有效。至少需要依次建立：reviewer 在目标任务上提供了可验证帮助；其帮助能被训练过程吸收；移除 reviewer 后收益在未见任务和不同长程分桶中保留；相同任务、token、更新次数与搜索预算的对照排除了数据量和选择偏差；多轮更新相对固定 Harness 带来额外收益。每一级失败都应单独报告，而不把“RSI 循环跑通”当成能力内化的证据。
