| environment / policies | 确定性 toy 环境、漂移学生、规则 reviewer | 不代表真实模型或真实教师 |

| hyperagents integration | append-only artifact lineage archive | 没有候选生成、选择或 RSI 外循环 |
| model_policy / student launcher | 固定 Qwen3.5-9B revision、独立 GPU worker、accepted-action 回调、EOS ID 停止；BF16 加载与真实 8 步链路通过 | 任务评分 1/5、未完成；thinking/64 步候选与 32K 输入未验收 |
| server/native acceptance | 单训练任务原生 CPU 初始化、公开 API、官方评分与重置负例通过 | 只执行可信官方代码，不作为生成代码执行入口 |
| execution/bubblewrap + worker | 普通用户 namespace、只读 runtime、seccomp、资源约束、跨步 Python 和管道 RPC；29 项执行端检查通过 | 不是形式化安全证明，也未覆盖新增依赖、网络或可写挂载 |
| integrations/appworld_rootless | reset/step/verify；公开 API broker、先停止再快照、独立官方 verifier；最新 13 项流程检查通过 | 只验收一个 train 任务；并非全量 benchmark |

原生环境准备入口是 `scripts/server/bootstrap_appworld_native.sh`；已安装后只重跑验收使用 `scripts/server/run_appworld_native.sh`，两者都调用 `accept_appworld_native.py`。结果与限制见 [原生验收记录](../environment/records/2026-10-26_AppWorld原生验收.md)。

当前生成代码执行入口为 `RootlessAppWorldEnvironment`，工程验收入口为 `scripts/server/run_appworld_rootless.sh`；安装入口为 `prepare_bubblewrap.py`。方案和证据见 [无 Docker 执行方案](../environment/无Docker执行方案.md) 与 [验收记录](../environment/records/2026-10-26_AppWorld无Docker验收.md)。

控制器、模型调用和 AppWorld world 在可信宿主侧；生成代码在 Bubblewrap 中，只能通过公开 API 代理交互。确认执行端退出后导出状态，独立 Python 进程评分；执行端不能提交真实 reward。模型 key 不进入执行端。

调用核心 runner 时必须用 `try/finally` 保证 `env.close()`，包括动作生成、审查或执行抛异常的路径。激活脚本只是选择 Python/缓存，直接执行普通 Python 文件不会自动进入沙箱。

## 真实实验的数据流

```text
Benchmark task
  -> environment reset/step/verify
  -> public observation
  -> student proposal
  -> private reviewer: PASS or REPLACE
  -> accepted action
  -> student-visible trajectory + private audit
  -> SFT/LoRA
  -> reviewer-free evaluation
```

环境 adapter 必须负责 reset、step、verify、公开观察和私有字段隔离；核心 runner 不应被 AppWorld 特殊逻辑污染。训练导出器只读公开训练 split，不读审查理由、私有 verifier 状态或最终测试信息。

## 参考仓库的采用边界

- Harness-Zero：采用执行前审查、PASS/REPLACE、接受动作与原始提议分离、学生轨迹与私有审计分离的工程思想。
- 无 Docker 路线参考其 client/world/verifier、公开 API 代理和退出后评分边界，用 namespace + seccomp + 管道替换 Docker/HTTP；不依赖 Harbor 调度器。
- HyperAgents：采用候选工件的父代、版本和评测关联；暂不假设其程序演化流程已经适合本项目。
- 两者都不直接成为本项目的研究贡献。贡献判断取决于真实失败机制、严格对照和 reviewer-free 内化证据。

## 下一步代码边界

1. 对已接通的真实学生验收正式 thinking/64 步候选 profile，检查格式、停止符、输入预算与成本；再扩展诊断任务，不把 8 步工程运行混作正式 B0。
2. 把学生、教师、K、h0、任务、预算和模型 revision 全部放入解析配置。
3. 为每次运行写 config_resolved、manifest、公开轨迹、私有审计、verifier 结果和 failure taxonomy。
4. 按许可扩展 3–5 个 API/依赖不同的诊断任务，先查兼容性，再区分模型失败和环境失败。
5. P0/P1 通过后，再实现真实 SFT/LoRA backend；先做保存/重载 smoke。
6. 最后再实现 K 的多轮更新和 A 的候选生成/选择。
